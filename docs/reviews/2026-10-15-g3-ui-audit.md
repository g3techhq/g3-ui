# g3-ui audit — October 15, 2026

Reviewed commit: `43ce21e`, crate version 0.5.1. The working tree was initially clean.

This is the pre-fix audit. The working-tree changes and validation are tracked
in [the resolution record](2026-10-15-g3-ui-fixes.md); findings below describe
the reviewed commit, and source line numbers refer to that version.

## Assessment

The architecture is sound and the public API is mostly coherent. The library already makes several good decisions for Android WebView: pointer tracking generally stays in JavaScript, shared gesture scripts use delegated listeners, most layouts use CSS rather than Rust measurements, images load lazily, and theme changes use custom properties. The source is readable, documented, and split along useful component boundaries.

There are real functional bugs. The most consequential are inconsistent overlay stacking and touch capture in swipe-enabled tabs. There are also state synchronization, picker validation, input, keyboard, and lifetime defects. I would fix those before describing the library as fully reliable across web and Android. I would retain the overall architecture.

Performance has not been measured on a device. A successful target check establishes compilation, not smooth scrolling, frame times, memory stability, soft-keyboard behavior, or TalkBack behavior.

## Prioritized defects

P1 means a high-impact broken interaction in an applicable configuration. P2 means a functional or accessibility defect under a specific supported use. P3 means a smaller correctness issue. “Source-confirmed” means the code path is identifiable; it does not mean it was exercised on Android.

### 1. P1 — Confirmations and toasts can appear behind a bottom sheet

**Evidence: source-confirmed, supported by browser stacking rules; visual reproduction pending.**

Bottom sheets and popovers enter the browser's top layer through `showPopover()`. `Modal` and `Toast` remain ordinary fixed elements with z-index values. An alert opened through `use_alert()` while a bottom sheet remains open is rendered in the app-level host, outside that sheet's top-layer wrapper. Its z-index cannot place it above the top layer. Toasts have the same limitation. Modals can also inherit clipping or containing blocks from transformed route ancestors.

The stylesheet explicitly promises that confirmations appear above sheets, so this breaks the intended contract. Use a common overlay stacking mechanism, with presentation order and focus ownership shared by sheets, popovers, modals, and toast hosting. Raising z-index alone will not fix it.

Sources: [sheet.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/sheet.rs:276), [modal.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/modal.rs:125), [overlay_host.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/overlay_host.rs:408), [overlay.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/overlay.rs:31). Platform reference: [MDN top layer](https://developer.mozilla.org/en-US/docs/Glossary/Top_layer).

### 2. P1 — Swipe-enabled tabs capture touches before a drag exists

**Evidence: source-confirmed; real touch reproduction pending.**

With `swipe: true`, `Tabs` calls `setPointerCapture()` on its outer wrapper on every non-mouse pointer press. This includes taps on nested buttons, links, and controls. Capture retargets subsequent pointer events and can retarget the click to the wrapper, preventing the intended child action. It is the same tap-breaking pattern the repository instructions explicitly warn against and `swipe.js` avoids.

Move tab gesture recognition into the shared gesture system. Acquire capture after movement crosses slop and horizontal intent is established, coordinate with nested gesture owners, and track the active pointer. Verify a plain touch tap inside the panel as well as a swipe.

Source: [tabs.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/tabs.rs:136). Platform reference: [MDN pointer events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events).

### 3. P2 — Native picker defaults use UTC instead of device local time

**Evidence: source-confirmed and observed on the host. This is an acknowledged implementation limitation in the date documentation.**

`CalendarDate::today()` and `TimeOfDay::now()` use browser-local time on WASM and UTC arithmetic on every native target, including Android. The audit probe printed `23:00` while the host's local clock was `19:00 -04:00`. Dates can differ near midnight. Initial native time pickers therefore show the wrong local time in non-UTC time zones. Server and browser renders can also disagree on today's calendar date.

Resolve native defaults with a local-time implementation, or introduce an explicit clock/default-value boundary that can be supplied by the renderer. Add tests around midnight, time-zone offsets, and SSR hydration. Keep the underlying date/time value types independent of time zones.

Sources: [datetime.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/datetime.rs:88), [native time branch](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/datetime.rs:238).

### 4. P2 — DatePicker can confirm a disabled date

**Evidence: source-confirmed.**

The wheel branch never passes `is_date_disabled` to `DateWheels`, and `commit` does not validate it. In dialog mode, opening initializes `draft_choice` to the selected date or today even when that date is disabled; OK is enabled whenever the draft is `Some`. Consequently, disabling a day in the calendar does not prevent confirming it. The default iOS wheel picker bypasses the predicate entirely.

Validate every commit against the current bounds and predicate. Define how wheel users navigate disallowed dates and what happens when no date is available. Validate the initial draft too.

Sources: [date_picker.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/date_picker.rs:216), [confirmation](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/date_picker.rs:299), [wheel branch](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/date_picker.rs:331).

### 5. P2 — Clearing a debounced input can emit the old query afterward

**Evidence: source-confirmed.**

Typing increments a generation counter and schedules `onchange(next)`. The clear button empties the signal and immediately calls `onchange("")`, but never invalidates that generation. Type a query, clear it before the debounce expires, and the old callback can still run afterward. A search consumer may display results for text that is no longer present. Programmatic changes also do not invalidate a pending typed value.

Put all value-changing paths through shared commit/cancellation logic. Clearing should cancel pending typed notifications. Add a timer-controlled test for type → clear → advance time, and define behavior for external value replacement.

Sources: [field.rs debounce](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/field.rs:165), [clear handler](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/field.rs:299).

### 6. P2 — A read-only input still offers a mutating clear action

**Evidence: reproduced in rendered markup, with the unconditional mutation verified in source.**

The clear button checks `clearable`, `disabled`, and non-empty value, but ignores `readonly`. Rendering `Input { readonly: true, clearable: true }` with text produces an enabled clear button. Its handler clears the caller's signal and emits change callbacks.

Suppress or disable the clear action for read-only fields and guard the mutation itself. This can share the input-path cleanup from finding 5.

Source: [field.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/field.rs:299).

### 7. P2 — Tabs ignores a replacement value signal

**Evidence: reproduced in a Dioxus VirtualDom.**

The manual context update compares `onchange`, `mode`, and `animated`, but omits the identity of `value`. Reusing a Tabs instance for another record can leave its children reading and writing the previous record's signal. A probe switched from a signal containing 1 to a different signal containing 2; after three update passes the rendered panel was still “Panel one.”

Use the same complete live-context equality pattern already used by `RadioGroup` and `SegmentGroup`. The repository already has a regression test for the equivalent historical radio-group bug; extend that protection to Tabs.

Source: [tabs.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/tabs.rs:118).

### 8. P2 — Several effects keep initial props after updates

**Evidence: source-confirmed under the repository's documented Dioxus effect semantics; individual runtime regressions still need tests.**

The code uses `use_synced_signal` well in many places, but misses several mutable plain props:

| Component | Initial value captured by an effect | Consequence |
| --- | --- | --- |
| Alert | `input.value` | Reopening a reused prompt can restore its original text instead of the new record's text |
| Toast | Computed `lifetime` | Switching duration, including persistent versus timed, can leave behavior inconsistent with current props |
| DatePicker | `min`, `max`, and the original controlled signal handle | A later opening can initialize its draft from old constraints or state |
| SheetFrame | `draggable` and `detent_signal` | Mounting with dragging disabled then enabling it can leave a visible handle unbound; a replacement detent signal can remain unused by the old listener |
| Refresher | Threshold and translated prompts | Updated props can disagree with gesture behavior and script-written labels |
| InfiniteScroll | Threshold margin | Updating the threshold does not rebuild observer geometry |

Track props that influence effects through synced signals, and explicitly reconfigure or replace scripts whose configuration changes. Keep using the current `EventHandler` handles; a handler handle and an ordinary captured scalar are different cases.

Sources: [alert.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/alert.rs:129), [toast.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/toast.rs:110), [sheet.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/sheet.rs:302), [refresher.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/refresher.rs:188), [infinite_scroll.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/infinite_scroll.rs:85).

### 9. P2 — Horizontal strips retain window listeners after unmount

**Evidence: source-confirmed and reproduced with the production script in a mock event environment.**

Each horizontal strip adds `pointermove` and `pointerup` listeners to `window`. Those closures retain the strip. There is no disposal path, abort signal, or connectedness check. Removing a shelf or scrollable segment therefore leaves two global listeners and its captured state. Repeated route visits accumulate listeners and retained nodes; every later pointer movement visits the old handlers. Toggling scrolling off also does not undo initialization.

Give per-element scripts an explicit lifetime: an AbortController for listeners, observer disconnection, timer/frame cancellation, and cleanup from `use_drop`. The probe removed the strip and still drove its drag state through the retained window handler. This is a concrete memory and event-processing issue, especially relevant to long-lived mobile sessions.

Source: [hscroll.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/hscroll.rs:116).

### 10. P2 — A sheet below its backdrop detent still traps keyboard focus

**Evidence: source-confirmed.**

SheetFrame correctly computes `modal = has_backdrop && !below_backdrop` for ARIA, scrim visibility, and scroll locking, but passes `has_backdrop` to the focus hook. At a low nonmodal detent, the page is described as usable and remains clickable while Tab is still trapped in the sheet. The focus hook also captures the initial trap flag, so merely passing a changing bool would not finish the fix.

Make focus modality follow the actual active detent and current backdrop policy. A change between modal and nonmodal behavior should reconfigure the focus session without stealing focus unnecessarily.

Source: [sheet.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/sheet.rs:219), [focus hookup](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/sheet.rs:285). Reference: [WAI modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

### 11. P2 — Calendar keyboard focus can land on an unfocusable disabled day

**Evidence: source-confirmed; browser keyboard reproduction pending.**

Arrow navigation clamps dates to bounds but does not handle the disabled-date predicate. The next date becomes the sole `tabindex="0"` day, yet its button can be natively disabled. The focus script then attempts to focus that disabled button. This can leave actual focus behind the internal cursor or leave no enabled day in the calendar's tab sequence. An initially disabled today/selected date has the same issue.

Either skip unavailable days with a bounded search or use a deliberate focusable `aria-disabled` grid-cell model. Test initial focus, month/year changes, an isolated disabled day, and a month with no available dates.

Source: [calendar.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/calendar.rs:158), [day markup](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/calendar.rs:338).

### 12. P2 — Time wheels can display a minute different from the saved draft

**Evidence: source-confirmed.**

With a minute step of five and a draft of 14:07, `TimeWheels` positions the wheel at 10 but keeps the draft at 07. Done can confirm 14:07 while 10 is visually selected. At 14:59 the search finds no minute at or after 59 and falls back to index zero, displaying 00 while still retaining 59. Behavior can depend on whether a scroll-settle message occurs before Done.

Choose a documented rounding policy and normalize the draft and displayed wheel selection together. Handle crossing an hour boundary explicitly if rounding upward. Test off-step values, 59 minutes, and immediate confirmation after opening.

Source: [time_picker.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/time_picker.rs:34).

### 13. P2 — Cancelled pull gestures can trigger refresh

**Evidence: reproduced with the extracted production script and mock touch events.**

`touchcancel` and `pointercancel` call the same `up()` routine as a completed release. Once a pull exceeds the threshold, cancellation therefore sends a refresh. A production-script probe dispatched touchstart, a 120px downward touchmove, and touchcancel; it received one refresh report. Window blur and mouseleave also use the committing release path.

Separate release from cancellation. Cancellation should restore the idle visual state without calling `on_refresh`. Also stop the refresher's polling timer on disposal: while the detached node still says refreshing, `settle()` otherwise keeps scheduling itself.

Source: [refresher.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/refresher.rs:90), [cancel listeners](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/refresher.rs:119).

### 14. P2 — AppWrapper disables page zoom globally

**Evidence: source-confirmed; browser enforcement varies.**

Every AppWrapper renders viewport metadata containing `maximum-scale=1.0, user-scalable=no`. That sets an accessibility-hostile policy for an entire consuming website, including pages that only need the library theme. Browsers or WebViews that honor it prevent users from enlarging content. Safe-area support does not require disabling zoom.

Preserve `viewport-fit=cover` while allowing zoom by default. If a particular native application needs a restrictive gesture policy, make that an explicit application choice.

Source: [app_wrapper.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/app_wrapper.rs:260). Reference: [MDN viewport metadata](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport).

### 15. P3 — TimeOfDay parsing silently ignores trailing fields

**Evidence: reproduced with the public parser.**

The parser reads the first two colon-separated segments without checking that no segments remain. `09:07:garbage` successfully parses as 09:07. A documented `HH:MM` parser should reject unsupported input rather than silently truncate it. Check iterator exhaustion and add malformed-input cases, including extra colons and seconds.

Source: [datetime.rs](C:/Users/Matthew/Documents/Files/Projects/g3-ui/src/components/datetime.rs:271).

## Web and Android performance

The implementation is appropriately structured for both environments, but “optimal” would require measurements. The highest-value work is:

1. **Fix listener retention and finish script disposal.** This is a known defect, unlike speculative micro-optimizations. Establish one setup/update/dispose convention for scripts and audit every observer, timer, and long-lived eval against it.
2. **Keep continuous gesture visuals in the WebView.** Swipe and reorder already do this well. Tabs should follow that pattern. The optional SwipeItem `on_swipe` path deliberately sends a Rust message on each move; document its cost or offer a limited update rate. Clock and rating still round-trip changed values before Rust redraws their visuals; measure those on a slower Android device before redesigning them.
3. **Measure long-list costs separately from pagination.** InfiniteScroll loads more rows but does not virtualize or bound mounted rows. Provide an integration pattern for windowed lists if consuming applications keep hundreds or thousands of complex rows mounted. A new virtualization API should be driven by an actual consumer workload.
4. **Measure effects and CSS on real screens.** Reorder writes transforms across its rows per move, and swipe changes a relational `:has()` selector on the content scroller. These can be reasonable, but need frame-time and style/layout measurements. Blur on iOS-mode FAB/navigation surfaces deserves a low-end-device check. Avoid declaring these bottlenecks from source alone.
5. **Review dependency features and delivered assets.** The Dioxus dependency enables its default launch, devtools, and logger features as well as router. Evaluate a library-appropriate feature set and an optional routing boundary. The timer dependency also enables default Dioxus features, so changing only g3-ui's declaration may not remove them. Source CSS is 182,845 bytes; measure the minified/compressed delivered file and parse cost before splitting the stylesheet. The single layered stylesheet is a useful contract worth preserving.
6. **Reduce allocations only where profiles justify it.** Theme and Strings reads clone owned values, several controls rebuild label vectors, and classes/styles are formatted on render. Shared immutable storage or memos may help dense repeated controls, but these are secondary to lifecycle defects and bridge traffic.

An Android test matrix should include long scrolling lists, repeated route mount/unmount cycles, swipe with interactive children, nested overlays, gesture cancellation, rotation, background/resume, IME opening and resizing, increased font size, TalkBack, and a hardware keyboard. Record WebView version, device, build mode, frame times, and memory before comparing changes. An ARM64 library check does not exercise any of these.

## API quality

The API's strongest parts are typed variants, generic typed selections, consistent `class`/`mode` conventions, useful slots, optional controlled state, and separate declarative and imperative overlay use. The shared Pressable abstraction also avoids repeating link/button semantics. Keep these.

The main API improvements are behavioral contracts:

- **Unify overlay ownership.** Provide a typed dismiss-top-overlay operation and a complete overlay stack, including modals, alerts, and popovers. `open_sheet_count()` plus a DOM selector makes Android Back depend on implementation details and does not describe every blocking overlay.
- **Document form semantics.** Input/TextArea can forward native form attributes. Select, DatePicker, TimePicker, Checkbox, and Toggle mainly operate through signals and custom elements; `required` on picker/select fields is currently a visual marker rather than native constraint validation, and they lack a consistent native form-name/value contract. Radio uses native inputs but does not serialize its generic value into an HTML value. Either document signal-driven form handling clearly or add a coherent form bridge.
- **Make event meaning consistent.** `onchange` means commit, debounce, every keyboard selection, or dismissal-related notification depending on the component. The distinctions can be valid, but a small shared contract table would help. Define whether owner-initiated closes call `on_dismiss`: Toast observes them; Modal and sheets primarily report user dismissals.
- **Define dynamic-prop support.** Current props appear ordinary and reactive while some scripts treat them as mount-time configuration. Fix finding 8, then state any intentionally static properties explicitly.
- **Complete mode propagation.** `Tabs` puts its explicit mode in the tab context for Tab buttons, but TabList resolves its own mode from ambient context. An explicit Tabs mode can therefore yield differently styled tab buttons and strip unless the caller also sets TabList's mode.
- **Finish localization.** Rating's spoken text is hard-coded English (`Not rated`, `of ... stars`) despite Strings being the central localization contract. Date formatting also fixes ordering/punctuation even when month and weekday names are translated; expose formatting hooks where locale conventions differ.
- **Keep public names stable.** There is little value in a broad naming or prop-type rewrite. Prioritize consistent behavior, form integration, and overlay operations over expanding the number of variants.

## Code quality and maintainability

The production code is generally clear. Shared FieldShell, Pressable, state helpers, and sheet infrastructure are worthwhile abstractions. Components are readable enough to trace interactions, and the documentation and playground coverage are stronger than the behavior tests.

The weakest area is the boundary between Rust state, script state, and browser state. Script strings, DOM flags, signal state, timers, and CSS animation state sometimes each own part of one interaction. A small internal script-session abstraction could centralize readiness, configuration updates, disposal, error reporting, and message lifetime without changing the public API.

Use existing helpers consistently. Tabs manually implements incomplete context synchronization; Img writes signals during render outside the sanctioned helper; Tab registers ordering state during its initial hook without removing or updating the registration when tabs change. The last case can make animation direction diverge from current DOM order after dynamic tab insertion/removal. These deserve focused follow-up rather than cosmetic restructuring.

Split or generate CSS source by component only if it improves maintenance while continuing to ship the documented single stylesheet. Avoid a rewrite that changes cascade ordering or overrides. Existing state modifier classes also differ from the repository's preference for data/ARIA styling; migrate them incrementally when touching the relevant component.

Do not rely on every eval failure being harmless. Most scripts currently discard errors. Development diagnostics should identify the component/script and initialization failure, with an intentional fallback for required capabilities. Avoid exposing internal diagnostics in normal product flows.

One suspected issue was explicitly ruled out: **a script returning does not by itself prove its later JS-to-Rust callbacks are broken.** The inspected native evaluator clears its globally indexed channel on completion, but registered callbacks can retain the channel object and still send. Comments saying native channels simply close on script return overstate that behavior. Audit the actual communication direction and cleanup requirements before changing all scripts to wait forever.

## Accessibility and test improvements

Markup coverage is useful, but role strings and ARIA attributes do not establish usable keyboard/touch behavior. Some existing script tests check source substrings, which cannot catch event retargeting, leaked listeners, or focus moving to a disabled element.

Add a browser interaction suite to the quality gate with a small, representative matrix of both modes, phone/wide widths, light/dark themes, reduced motion, and touch input. Prioritize regressions for findings 1–14 over expanding snapshot counts. Add mounted Dioxus tests for signal replacement and changed props across all effect-driven controls.

Additional focused checks:

- Horizontal TabList currently intercepts both Up/Down and Left/Right in the shared roving script. The [WAI tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) leaves Up/Down available for page scrolling in horizontal lists. Make keyboard behavior depend on the actual widget and orientation.
- Leaving TabPanels are `aria-hidden` but remain mounted during animation without `inert`. Interactive descendants can remain keyboard-reachable during that interval; test and make them inert until current again.
- Verify focus return after close, nested overlay Escape handling, and hidden-page scheduling. The focus helper uses a frame callback for initialization and checks current focus during cleanup; actual browser timing matters.
- Test RTL as a complete interaction path. Several gesture scripts use physical left/right geometry or nonnegative scroll offsets, while the API describes logical start/end and the keyboard helper partly handles RTL. Treat support as partial until the full path is verified.
- Specify minimum browser/WebView capabilities. Popover has a fallback, but the fallback does not provide equivalent clipping/stacking guarantees. Container queries, `:has()`, color mixing, and other modern CSS features also need a tested compatibility policy.

## Recommended sequence

1. Fix overlay stacking and tab touch capture, with real touch and nested-overlay tests.
2. Fix input clear behavior, Tabs context replacement, native local-time defaults, and picker commit validation.
3. Establish script update/disposal conventions; fix retained listeners and cancellation behavior.
4. Fix sheet modality, calendar keyboard focus, minute-step normalization, zoom defaults, and remaining dynamic-prop gaps.
5. Add browser and Android runtime coverage, then use profiles to choose performance changes.
6. Make additive API improvements for forms, overlay dismissal, localization, and documented event semantics.

The passing checks are a good baseline. They coexist with the reproduced bugs because the current suite mainly protects compilation, static markup, and selected helper logic. No source fixes or releases were performed during this audit.
